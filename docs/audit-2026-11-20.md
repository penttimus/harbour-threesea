# Threesea security, performance and battery audit

Reviewed the 0.4.0 source tree at `370bddd` on 2026-11-20. The first fixes should protect backup recovery and existing files in the export folder. For battery use, the most actionable changes are stopping background positioning, removing duplicate group-call requests and reducing the work done on every connected wake.

## Backup integrity and security

### High — a successful backup can contain a chat that Threesea will skip on restore

The Android-format writer serializes an entire conversation to one CSV entry. It imposes no corresponding restore-size check before reporting success and rotating older backups. The production importer caps each table at 64 MiB of expanded data. It skips the entire oversized chat, records the omission and continues. A highly compressible chat can cross the limit even when the ZIP looks small. There is also a 400,000-entry archive-wide limit on the reader. The consequence is most serious when the user relies on the success notification to erase or replace a phone. [Writer](../core/src/android_backup/export.rs#L749) · [Completion and rotation](../core/src/android_backup/export.rs#L380) · [Table limit](../core/src/android_backup/import.rs#L43) · [Restore behavior](../core/src/android_backup/import.rs#L375) · [Entry limit](../core/src/android_backup/archive.rs#L157)

Share the reader's compatibility limits with the writer. Until larger backups can be restored with bounded memory and authenticated input, detect the limit before publishing success, identify the affected chat to the authorized user and retain the last restorable backup. Test export followed by restore on both sides of the limit.

### High — backup retention can delete another identity’s backups

The folder picker accepts an existing directory. Rotation recognizes ownership solely from the timestamped filename and keeps three by default. When a user reuses an SD-card directory for a new identity, or copies a second phone's backups into it, the next successful export can delete those other archives as the oldest matching files. Their contents and provenance never enter the decision. [Folder selection](../qml/pages/DataBackupPage.qml#L47) · [Retention default](../core/src/app_android_backup.rs#L2503) · [Filename recognition](../core/src/android_backup/export.rs#L71) · [Deletion](../core/src/android_backup/export.rs#L446)

Track completed exports in the encrypted store, or give each installation a dedicated randomly named directory. Rotate only files known to belong to that backup set. Treat existing untracked archives as user files during migration.

### Medium — temporary export files can overwrite other writable files

Both exporters create a predictable, second-resolution `.part` path with truncating file creation after a separate cleanup pass. In a destination writable by another process, the directory entry can change between cleanup and open. On a filesystem supporting symlinks, creation can follow a link and truncate a file the app has permission to write. Ordinary final rename can also replace an existing same-second export. Chat-export cleanup separately deletes every filename matching a broad prefix and suffix. The shared-directory issue requires local write access to the destination. [Chat export creation](../core/src/app_chat_export.rs#L85) · [Publication](../core/src/app_chat_export.rs#L228) · [Cleanup](../core/src/app_chat_export.rs#L290) · [Data backup creation](../core/src/android_backup/export.rs#L336)

Use exclusive creation with an unpredictable temporary name and owner-only permissions where supported. Publish without replacing an existing file, and tie cleanup to files the exporter created. For plaintext chat exports, handle interrupted runs explicitly. A killed process skips the temporary file's destructor, and current cleanup waits for another chat export.

### Medium — the standalone library dependency scan fails

RustSec database `f291af9` (2026-11-20, 1,555 advisories) reported zero vulnerabilities for the app's 332 locked packages. The standalone vendored library lockfile has 337 packages and returned seven vulnerabilities plus four informational warnings. The RPM build uses the root lockfile. The library's independent tests and the weekly audit use the second one. Update the vendored resolution, then rerun its tests and both scans. Yanked-package status and platform-provided libraries are outside these two offline scans. ## Battery and network activity

### Medium — positioning can continue after minimizing the app

The send-location dialog requests a position every second and runs a second one-second timer while the source is active. The binding checks the app lock, dialog status and whether a picker is open. A Sailfish page can stay active behind another app, and the picker flag stays set until returning to the dialog. With no immediate app lock, switching away can therefore leave positioning requested. The nearby-places page can also request a lookup when a better class of fix arrives. [Position source and timer](../qml/pages/SendLocationDialog.qml#L69) · [Picker lifetime](../qml/pages/SendLocationDialog.qml#L155) · [Nearby request](../qml/pages/PlacePickerPage.qml#L32) · [Foreground handling elsewhere](../qml/pages/ChatPage.qml#L412)

Gate positioning and lookups on foreground application state, then reacquire a recent fix on return. Verify the positioning indicator and requests with the picker open, minimized, screen locked and resumed.

### Medium — a visible group call banner polls the call server twice

In the Full flavour, the Rust core starts a watcher per group with a running call. After a successful check it waits ten seconds and checks again, even with the chat closed. Opening that group's chat starts a second ten-second QML timer. Both paths fetch state from the group-call server and publish it. The guard on the Rust watcher prevents a second watcher, but each UI request still performs a refresh first, and slow requests can overlap. At low latency this approaches twelve polling rounds per minute for one visible group with one running call. [Core watcher](../core/src/app_group_calls.rs#L221) · [Server request](../core/src/app_group_calls.rs#L366) · [UI command](../core/src/app_group_calls.rs#L812) · [Chat timer](../qml/pages/ChatPage.qml#L1818)

Let the banner consume the existing watcher events. Coalesce any immediate refresh on opening or reconnecting with an in-flight request for the same group.

### Medium — a routine background wake scans historical file messages

With background delivery enabled, the app requests an aligned wake every five minutes. Every connected wake calls the media retry query. The download half evaluates JSON state across historical file messages, including completed downloads, to discover whether anything needs attention. A host SQLite 3.46.1 query-plan check with the app's file indexes selected `SCAN messages USING INDEX messages_files`. With 100,000 synthetic completed file messages and zero retries, the warm in-memory median was 15 ms over seven executions. Disk reads, SQLCipher and mobile hardware can change the cost substantially. [Wake scheduling](../qml/harbour-threesea.qml#L869) · [Wake handler](../core/src/app_messages.rs#L681) · [Connected retry](../core/src/app_media.rs#L2124) · [SQL](../core/src/app_media.rs#L565) · [Indexes](../core/src/messages.rs#L303)

Index only rows with a pending retry deadline or maintain a small retry table transactionally. Check the empty-queue query plan and preserve recovery after suspend, restart and network changes. Keep the delivery wake interval while measuring the effect of reducing its workload.

### Medium — losing all network routes leaves periodic connection work enabled

The bridge already collects active network identifiers. Losing the last one starts the same wake timer as acquiring a new one, and the core only receives the Wi-Fi/metering flag. The background job stays enabled whenever the account is ready and background delivery is on. With no network for hours, the app still requests five-minute wake opportunities and the connection loop can keep attempting login while awake. Ordinary retry backoff tops out at one minute. This adds work in airplane mode or prolonged loss of coverage. The platform can coalesce requested wakes, so actual device wake frequency needs measurement. [Network changes](../bridge/threesebackend.cpp#L377) · [Core network state](../core/src/app.rs#L2530) · [Background job](../qml/harbour-threesea.qml#L869) · [Reconnect loop](../core/src/connection.rs#L1416) · [Backoff](../core/src/connection.rs#L1309)

Pass an explicit offline state to the connection loop and pause network probes while all routes are known to be down. Resume promptly when a route returns. Preserve separately due local maintenance and a recovery path for missed connectivity signals.

### Low — a pending navigation action polls a locked database every 300 ms

Opening a link or share while waiting for the database passphrase leaves work pending. The timer checks the separate UI lock in its running condition, then returns from every tick when the database is locked. It can run for the whole time the passphrase prompt waits, roughly 200 callbacks per minute while the event loop runs. These callbacks do not themselves demonstrate wakeups from deep sleep. Dispatch pending work on backend-state and page-stack transitions, including terminal errors. [UI lock](../qml/harbour-threesea.qml#L48) · [Pending navigation](../qml/harbour-threesea.qml#L807)

## Performance and memory

### High on large histories — exports retain the whole conversation

Chat export reads 500 messages at a time but pushes every page into a vector, then builds the complete transcript while the messages are still resident. Android-format export requests up to `u32::MAX` messages for one chat, builds the entire CSV and collects attachment references. Its per-chat conversion loop performs synchronous work on the same single-threaded runtime that drives the connection. Large histories can stall message processing or exhaust a phone's memory, including during scheduled backups. [Chat history](../core/src/app_chat_export.rs#L241) · [Transcript](../core/src/app_chat_export.rs#L101) · [Android CSV](../core/src/android_backup/export.rs#L757) · [Runtime](../core/src/runtime.rs#L98)

Page forward using the existing history ordering and a stable upper boundary. Feed bounded chunks into the ZIP writer, using separate bounded passes as needed for media. Preserve private-chat lock checks, cancellation, and authenticated output. Measure peak RSS and connection responsiveness during export of a single long chat.

### Medium — two-character global searches block the core

The UI submits a search from two characters after a 300 ms debounce. The trigram index needs three characters, so the shorter path can scan the full history for an absent term on the core thread. The repository benchmark over 100,000 messages in 1,000 chats gave these warm host medians over five runs in the debug test build. Other audit checks ran concurrently. [UI threshold](../qml/pages/SearchPage.qml#L56) · [Query selection](../core/src/messages.rs#L1203) · [Benchmark fixture](../core/src/messages.rs#L3303)

| Operation | Median |
| --- | ---: |
| Load conversation summaries | 22.04 ms |
| Indexed search, no match | 0.17 ms |
| Indexed search, 50 hits | 7.29 ms |
| Two-character search, no match | 204.61 ms |

Keep two-character searches available for short names and words. An explicit submit for short global message searches would avoid the scan while typing a longer term. A cancellable query on a separate encrypted read connection would also preserve responsiveness.

### Medium — profile and group picture preparation runs on the GUI thread

Choosing a picture synchronously decodes, crops, scales and JPEG-encodes it through the QML-callable setter. A profile picture additionally gets a second Safe-sized JPEG. Sizing by the shorter dimension leaves the larger dimension unconstrained for panoramic images, and images with a short side of 1,024 pixels or less skip decode scaling entirely. Move preparation to the file worker pool and bound decoded pixels before allocating. Test with a normal camera photo and a panorama while scrolling or receiving a call. [Picture setters and processing](../bridge/threesebackend.cpp#L1079) · [Existing worker path](../bridge/threesebackend.cpp#L1048)

### Low — backups recompress media that is already compressed

Both exporters use DEFLATE for every media entry, including JPEG, PNG and encoded video. This repeats on scheduled backups. As an illustration, host zlib level 6 saved 16,482 bytes (0.31%) on the 12 PNGs in the repository screenshot directory. Use ZIP Stored for recognized already-compressed media, retain AES when enabled and keep compression for text. Verify Android restore compatibility and compare export time and energy on a media-heavy backup. [Data backup media](../core/src/android_backup/export.rs#L798) · [Chat ZIP writer](../core/src/app_chat_export.rs#L305)

## Verification and remaining coverage

The review traced the Rust core, Qt bridge and QML paths for stored secrets and private chats, notification actions, links and sharing, pinned network requests, media handling, backup and restore, chat queries, calls, location, and background scheduling. It also checked dependency resolution and release configuration. Assurance for protocol behavior comes partly from the existing suites. Platform libraries, every upstream implementation, and the production service were outside the source review.

The quick repository checks passed, including logging, formatting and the match of all 20 TLS pins across five domains. The QML/core consistency check and Clippy passed, including Clippy with and without the demo feature. With loopback sockets available, 1,196 core tests passed and 19 were ignored by the default suite. The large-history benchmark ran separately. All 3,706 standalone libthreema library tests passed.

Fifteen Sailfish SDK suites passed, including lock-state transitions, notification tokens, Secrets handling, page loading, media, and the map renderer's pinned local HTTPS cases. The call-engine target also built. Runtime call quality, camera and audio routing still need a phone. Automatic approval review rejected the combined SDK run because its lifecycle test starts a privileged root container with the host PID namespace. That test was excluded from the separate runs. Fuzz campaigns, AddressSanitizer, and a release RPM rebuild were outside this pass. [SDK runner](../scripts/run-sdk-tests.sh) · [Lifecycle test](../scripts/test-lifecycle.sh#L14)

Battery impact is inferred from active resources, network paths, query plans and timer rates. To quantify it, compare screen-off discharge and CPU awake time on the same unplugged phone and network, with background delivery enabled, between the current and corrected builds. Include an empty retry queue with a large media history, a minimized location picker and an announced group call. Record positioning time, server requests and message delivery latency alongside discharge. [Existing device checklist](voice-video-device-checklist.md#o-battery-and-the-connection-a-whole-day)
